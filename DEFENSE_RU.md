# Защита: Strategy Pattern

## Короткое объяснение (около минуты)

«Я рассматриваю калькулятор. Семейство алгоритмов — сложение, вычитание и умножение.
Общий интерфейс OperationStrategy содержит execute. Calculator — Context: хранит
ссылку на интерфейс и делегирует вычисление. Client выбирает конкретную стратегию.
Через setStrategy я меняю алгоритм во время работы у одного объекта Calculator.
Контекст не проверяет тип стратегии и не содержит if/switch для выбора операции».

Это образец объяснения архитектуры, а не заявление о самостоятельном авторстве.
В репозитории раскрыта AI-помощь; правила курса разрешают AI только как reference.
Нужно понимать каждую строку и соблюдать правила преподавателя.

## Демонстрация

1. Выполни команды build/run из README с JDK 17.
2. Открой OperationStrategy: покажи общий контракт.
3. Покажи AddStrategy, SubtractStrategy, MultiplyStrategy: по одному алгоритму.
4. Открой Calculator: private поле, конструктор, setStrategy, calculate.
5. Открой Client: один new Calculator, затем две смены стратегии.
6. Запусти Client: 16.0 → 8.0 → 48.0. Объясни, почему меняется результат.
7. Запусти CalculatorTest: 19 проверок.
8. Скомпилируй examples/extension и запусти ExtensionClient, ExtensionTest.
   Деление дает 3.0; еще 6 проверок. Покажи, что core-классы не меняются.
9. Покажи UML и шесть принципов в REPORT.md.

## Частые вопросы

**Что такое Strategy?** Поведенческий паттерн: семейство взаимозаменяемых алгоритмов
за одним интерфейсом; Context делегирует выбранному алгоритму.

**Где composition?** Calculator содержит OperationStrategy, вместо наследования
от конкретного алгоритма.

**Где runtime switching?** setStrategy заменяет ссылку в уже созданном Calculator.
Новый Context не создается.

**Почему нет if/switch?** Полиморфизм выбирает реализацию execute. Client знает
конкретные стратегии, Context работает через интерфейс.

**Чем отличается State?** Strategy меняет выбранный алгоритм. State отражает
состояние объекта и переходы его жизненного цикла. Пример State: New → Paid →
Shipped. Стратегии калькулятора не управляют переходами друг к другу.

**Как добавить операцию?** Создать класс implements OperationStrategy, реализовать
execute и выбрать его в клиенте. В примере DivideStrategy и отдельный ExtensionClient.

**Какие Clean Code принципы?** Понятные имена; одна ответственность; короткие методы;
Open/Closed; инкапсуляция и валидные объекты; зависимость от абстракции.
Для каждого есть конкретный excerpt и объяснение в отчете.

**Что будет при null?** Objects.requireNonNull немедленно выбросит исключение.
При неудачном setStrategy старая стратегия сохранится.

**Почему double?** Просто для демонстрации. Есть округление, NaN и infinity.
Для денег нужна отдельная модель точности; этот проект не финансовый калькулятор.

**Почему division проверяет ноль?** Это правило конкретного алгоритма, поэтому
проверка находится в DivideStrategy, а не в Calculator. right == 0.0 ловит и -0.0.

**Цена паттерна?** Больше классов и настройка в Client. Для маленького фиксированного
набора операций это может быть избыточно; при расширении алгоритмов дает гибкость.

**Можно lambda?** Да, интерфейс имеет один abstract method. Основные стратегии
оставлены отдельными классами для наглядности, lambda показана только в тесте.

## Мини-проверка понимания

Перед защитой без подсказки объясни вызов calculate, нарисуй направления стрелок UML,
добавь простую новую операцию и объясни отличие Strategy от State.
Оценка защиты зависит от понимания, не только от наличия файлов.
